# API keys

Use one named key per client/device. Keys contain 256 random bits generated by the operating system. TLS encrypts transport; the key authorizes inference. Both are needed for LAN use.

```powershell
.\ninfer-manager.cmd -Action CreateKey -ClientName hermes-laptop -ExpiresDays 90
.\ninfer-manager.cmd -Action ListKeys
```

Creation displays the key once. Save it directly in that client's protected secret store. Listing shows only ID, label, creation, expiry, and revocation times. Lost keys cannot be recovered: create a replacement and revoke the lost one.

`ExportHermes` adds Qwen to the existing default Hermes home. It creates a dedicated key and writes only `HERMES_CUSTOM_QWEN_API_KEY` to that home's ACL-restricted `.env`, without displaying the key or changing the saved ChatGPT model. It explicitly targets the default home even when a different profile is sticky. Configuration, environment, key ID, and the public certificate are backed up first. Failed setup restores their previous contents, removes files that did not exist before, and revokes only the failed setup's new key.

Re-running `ExportHermes` creates another key. Previously issued keys remain valid until you explicitly revoke their IDs with `RevokeKey`; unrelated device keys are never revoked automatically.

## Rotate without interrupting work

```powershell
.\ninfer-manager.cmd -Action RotateKey -KeyId hermes-laptop-EXAMPLE -ExpiresDays 90
```

Update the client with the replacement and test it, then revoke the old ID:

```powershell
.\ninfer-manager.cmd -Action RevokeKey -KeyId hermes-laptop-EXAMPLE
```

Rotation deliberately keeps the old key valid until explicit revocation. This is a short, operator-managed overlap, not automatic expiry. Revocation and expiry are checked for every new HTTP request and need no GPU restart. Already-active streams may finish.

## Storage and boundaries

- `config/manager/runtime/clients.json` stores SHA-256 verification hashes of high-entropy keys, never their plaintext values.
- Separate local-manager and backend credentials are stored in restricted files under `config/manager/`.
- NInfer reads its backend credential from a read-only TOML file. Credentials are absent from process arguments, Docker environment variables, Compose configuration, and diagnostics.
- The configuration directory's ACL permits the owning Windows user and SYSTEM. Docker administrators can read mounted secrets and are trusted operators.
- Hermes `.env` files and backend files contain plaintext secrets protected by filesystem access controls. This is not a claim of cryptographic encryption at rest. Use full-disk encryption and secure backups where required.
- Caddy's persistent volume holds private TLS material. Export only the public certificate, never that volume to a client.
- Authorization headers and request bodies are not logged by the proxy. NInfer's operational logging omits prompt/answer text.
- Detailed NInfer request JSONL is disabled by default because its generated token IDs can reveal answer content. Treat any deliberately enabled detailed logs as private data.

The `manager-local` credential is reserved for manager diagnostics. Device keys all belong to the same trusted owner; they do not isolate NInfer's stored Responses, sessions, or shared model memory into separate tenants.

Original NInfer-Ext credentials remain in their original configuration for rollback. They do not authenticate to the new gateway. Rolling back the engine never restores revoked new-manager keys.
